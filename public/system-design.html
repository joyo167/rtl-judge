2 · Request Flow — What happens when a user submits code

1
User clicks Submit
Monaco editor sends code to the Next.js API
2
POST /api/submissions
Next.js route handler receives code + problemId + userId
3
Save to PostgreSQL as pending
Prisma inserts a Submission row with verdict = "pending"
4
Push job to Redis queue
BullMQ enqueues job with submissionId, code, testbenchCode into the submissions queue
5
Return submissionId ~100ms
API responds immediately — judging is async. Frontend starts polling.
6
EC2 worker picks up the job
BullMQ worker on EC2 pulls the job from Redis and writes solution.v + testbench.v to /tmp/jobs/<id>/
7
Docker container runs iverilog
Sandboxed container compiles + simulates with limits: 256 MB RAM · 1 CPU · 50 PIDs · no network · 5s timeout
8
Verdict written to PostgreSQL
Judge parses stdout → AC / WA / CE / TLE / RE. Updates Submission row. If AC + first solve, awards points and updates Redis leaderboard.
9
Frontend poll detects verdict
GET /api/submissions/[id] polling every ~1.5s sees verdict ≠ "pending" and renders the result

3 · Key Design Decisions

Decision Reasoning
Why EC2, not Vercel for the judge? Vercel is serverless — functions can't hold a persistent BullMQ worker connection or access a Docker daemon. EC2 is a persistent VM with full OS access, Docker installed, and PM2 to keep the process alive across crashes and reboots.
Why Redis sorted sets for the leaderboard? Redis sorted sets use a skip list internally — every score update is O(log N), the set stays ordered at all times with no re-sorting. Fetching the top 100 is O(log N + 100). A PostgreSQL ORDER BY points DESC at scale would be significantly heavier.
Why Docker containers, not raw exec()? Raw exec() runs untrusted Verilog directly on the EC2 host — a malicious submission could read files, make network calls, or exhaust resources. Docker provides full isolation: read-only bind mount, no network, PID/memory/CPU limits, and AutoRemove so containers can't accumulate.
